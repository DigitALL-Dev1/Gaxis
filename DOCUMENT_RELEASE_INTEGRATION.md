# Document approval and release

The Release Queue at `/admin/release` uses the actual FastAPI endpoints below. It lists submitted versions for assigned reviewers, and all active families for document administrators. The sidebar and route gate accept `documents.review` or `documents.release`. The former permits review and returns; only the latter permits publication. The backend independently checks permissions, current family assignment and status. Ordinary document owners and preparers cannot decide their own reviews, even with both permissions. Administrators have an explicit approval exception. The bootstrap Basic administrator can approve and return pending documents across active families. Registered users with an active SYSTEM_ADMIN role and documents.release permission have the same document review scope. Admin decisions record the authenticated identity, email and reviewer kind; Basic decisions use a bootstrap:email actor identifier rather than impersonating a registered user. When an Admin approves their own preparation, the UI identifies the Administrator override and the backend persists self_review_override=true in the review record. The same applies to registered SYSTEM_ADMIN users with release permission.

| Method | Route under `/api/v1/lumen`               | Action                                           |
| ------ | ----------------------------------------- | ------------------------------------------------ |
| GET    | `/release-queue`                          | Pending versions with document metadata          |
| GET    | `/release-queue/{version_id}`             | Review details and decision capabilities         |
| GET    | `/document-versions/{version_id}/file`    | Authorized uploaded bytes, no public storage URL |
| POST   | `/document-versions/{version_id}/release` | Approve and publish                              |
| POST   | `/document-versions/{version_id}/return`  | Return for correction                            |
| GET    | `/documents/{document_id}/reviews`        | Owner/reviewer approval history                  |

Both decisions take JSON `{ "review_comments": "..." }` (maximum 10,000 characters). A return requires non-whitespace comments. The UI confirms approval, disables decisions and closing while saving, displays backend errors, preserves comments after failure and refreshes the queue on success. PDF files preview inline; Word files download for review. File requests use the authenticated API client; temporary object URLs are revoked when the review closes.

Release sets the candidate to `APPROVED_CURRENT`, records the reviewer name/ID and release timestamp, supersedes the previous approved version and updates the current pointer. The library fetches the newly published pointer when opened or refreshed. Reviews share the per-document upload reservation, reject competing decisions and reject repeat/stale decisions with 409. Failed publication writes compensate version status changes. Pending or returned versions never enter the employee library. The media module's processing/licensing/captions validation hook runs before publication of a media-backed version.

A return sets `RETURNED_FOR_CORRECTION`, retains review comments and leaves the approved pointer unchanged. The owner sees the comments in My Prepared Documents and in approval history. **Correct and resubmit** opens a new revised upload: enter a new distinct version number, required change summary and corrected file. Title, classification, audience and acknowledgement corrections are saved on the new pending version, shown to reviewers and applied to published metadata only on release. Family/reference remain fixed. Prior returned versions and their review evidence remain visible.

Restart the backend on port 8001 to load these new endpoints. Set `UPLOAD_DIR` to the same directory used for preparation; missing files produce a visible file error. Ordinary reviewer role permissions must include `documents.review` and/or `documents.release`, and the family must assign that reviewer. The Basic Admin can review across active families; registered SYSTEM_ADMIN users need documents.release. No automatic permission or family assignment is created by this integration.

Tests use temporary uploaded files and mocked collections, with real FastAPI cookie sessions. They cover independent approval, administrator approval/audit identity, reviewer permissions, family scope, required return comments, correction/resubmission, supersession, published/pending separation, preview authorization, competing requests and failed publication rollback. Frontend tests cover API contracts, preview, confirmation, errors, disabled actions and owner history. No live reviews or documents are changed by tests.
